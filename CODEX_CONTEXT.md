# Контекст проекта Chatbot Walrus для Codex

Обновлено: 28 сентября 2026 года.

## Статус и обязательное ограничение

Проект находится на стадии планирования.

**До отдельной явной команды пользователя запрещено:**

- создавать или инициализировать Git-репозиторий;
- писать исходный код, конфигурацию, скрипты, тесты или инфраструктуру;
- устанавливать зависимости, регистрировать внешние сервисы, создавать кошельки или выполнять деплой;
- менять архитектуру и расширять объём MVP без согласования.

Сейчас разрешены только изучение официальной документации, уточнение требований и подготовка плана. Следующая реализация должна начинаться только после прямой команды пользователя.

## Цель проекта

**Chatbot Walrus** — простой персональный Telegram-ассистент для хакатона **Walrus Sessions: Chatbots That Remember**. Его ключевая ценность — не обычный чат с LLM, а долговременная память, которая сохраняется между отдельными разговорами и сессиями и заметно влияет на последующие ответы.

Короткое продуктовое обещание:

> Расскажи один раз — бот вспомнит это в следующей сессии.

Walrus Memory должна быть центральной частью продукта и демонстрации, а не декоративной интеграцией.

## Зафиксированный MVP

Основной поток:

```text
Telegram
  -> Telegram Bot API
  -> Node.js + TypeScript backend
  -> Walrus Memory: recall релевантных воспоминаний
  -> LLM с воспоминаниями и контекстом текущего диалога
  -> ответ в Telegram
  -> анализ нового сообщения и сохранение полезных фактов в Walrus Memory
```

Первый интерфейс — только Telegram. Отдельный веб-фронтенд для MVP не нужен.

Предварительный стек, который нужно подтвердить перед реализацией:

- Node.js и TypeScript;
- grammY или Telegraf для Telegram Bot API;
- Vercel AI SDK для вызова модели и возможной интеграции `withMemWal`;
- LLM-провайдер выбирается отдельно (OpenAI, Anthropic, OpenRouter или альтернативная модель);
- пакет `@mysten-incubation/memwal` и Walrus Memory;
- managed production/mainnet relayer как самый простой стартовый вариант; self-hosted-инфраструктура не входит в MVP;
- простой хостинг, доступный реальным пользователям (конкретный провайдер пока не выбран).

## Требования к долговременной памяти

1. Память должна переживать перезапуск бота, завершение Telegram-диалога и новую пользовательскую сессию.
2. Перед генерацией ответа бот должен искать релевантные воспоминания и добавлять только полезные результаты в контекст LLM.
3. После сообщения пользователя бот должен извлекать и сохранять только факты, полезные в будущем. Не следует записывать весь чат подряд.
4. Предпочтительные категории памяти:
   - профиль пользователя: имя, язык, род занятий, интересы;
   - предпочтения: формат ответов, инструменты, технологии;
   - цели;
   - проекты и задачи;
   - важные события, договорённости и решения.
5. Память разных Telegram-пользователей должна быть строго изолирована. Базовая модель изоляции MemWal — `owner + namespace`; предварительно предполагается отдельное пространство вида `telegram:<user_id>` для каждого пользователя. Точную стратегию namespace нужно проверить по актуальному SDK перед реализацией.
6. Нерелевантные результаты recall не должны безусловно попадать в prompt: нужны лимит результатов и порог релевантности.
7. Запись памяти может быть асинхронной. Интерфейс не должен надолго блокировать ответ пользователю; при реализации нужно предусмотреть наблюдаемость ошибок и незавершённых записей.
8. Пользователь должен понимать и контролировать память. Минимальные команды-кандидаты:
   - `/start` — объяснить назначение бота;
   - `/help` — показать помощь;
   - `/remember <факт>` — явно сохранить факт;
   - `/memory` или `/memories` — показать, что бот помнит, насколько это позволяет API;
   - `/forget` — удалить или исключить память, если актуальный API поддерживает нужную семантику.
9. Нельзя обещать физическое удаление данных без проверки актуального поведения MemWal/Walrus. Нужно различать удаление из индекса recall и жизненный цикл blob в Walrus.
10. Секреты (`MEMWAL_PRIVATE_KEY`, токены Telegram и LLM, и другие credentials) должны оставаться только на сервере и не попадать в Git.

## Главный demo-сценарий

Демонстрация должна за 30–60 секунд доказать, что память реально влияет на ответ.

Сессия 1:

> Пользователь сообщает имя, сферу работы, текущий проект и предпочтение TypeScript. Бот подтверждает сохранение важных фактов.

Затем диалог закрывается или начинается новая сессия.

Сессия 2:

> Пользователь спрашивает, что бот о нём помнит, а затем просит предложить стек для проекта.

Успешный результат: бот корректно вспоминает факты из первой сессии и использует предпочтение TypeScript в новой рекомендации. Для конкурсной демонстрации нужны проверяемые доказательства: скриншоты, логи разговора, видео или live-ссылка.

## Что сознательно не входит в первый MVP

- собственный React/web-интерфейс;
- сложная Web3-авторизация;
- NFT, токен, DAO или собственный Move-контракт;
- отдельная RAG-система;
- голосовой интерфейс;
- multi-agent архитектура;
- self-hosted Walrus Memory relayer;
- сложная аналитика и второстепенные интеграции.

Сначала требуется довести до надёжной работы один цикл:

```text
пользователь сообщает важный факт
  -> бот сохраняет его в Walrus Memory
  -> начинается новая сессия
  -> бот находит факт
  -> факт заметно улучшает ответ
```

## Правила хакатона Chatbots That Remember

Ниже — рабочее резюме официальных правил на 28 сентября 2026 года. Перед финальной подачей правила и формы нужно проверить ещё раз на официальной странице.

- Организатор и спонсор: Walrus Foundation.
- Период хакатона: с 18 сентября 2026 года, 09:00 UTC, до 9 октября 2026 года, 14:00 UTC.
- Объявление результатов: 16 октября 2026 года.
- Участник должен соответствовать возрастным и территориальным требованиям правил, зарегистрироваться на DeepSurge и сделать не более одной подачи на человека или команду.
- Подача должна быть работающим чатботом, который использует Walrus Memory для хранения и вызова контекста между разговорами. Telegram прямо указан как допустимый канал.
- Бот должен быть развёрнут и доступен реальным пользователям как минимум через один канал.
- Вся конкурсная память должна храниться в Walrus на Mainnet.
- К моменту подачи Walrus Memory agent должен записать минимум **10 blobs в Mainnet**. В форме нужно указать agent ID и число blobs как подтверждение.
- Нужен публичный GitHub-репозиторий с исходным кодом и инструкциями по запуску. Его следует создать только после отдельной команды пользователя, несмотря на то что он потребуется к финальной подаче.
- В подаче нужно указать используемую LLM.
- Нужен отдельный wallet address, созданный для Sessions.
- Нужно опубликовать статью на Medium или Inkray: что делает бот, как интегрирована Walrus Memory, чем поведение отличалось до и после добавления памяти, а также доказательства реального использования.
- Нужно заполнить feedback form по Walrus Memory, указав как минимум одну проблему/точку трения и одну идею улучшения; релевантные технические проблемы можно оформить в GitHub репозитории MemWal.
- Нужно вступить в Walrus Discord и поделиться статьёй в X, отметить `@WalrusProtocol` и использовать `#WalrusMemory` под анонсом сессии.

Основные критерии оценки:

1. **Does it actually remember?** Память должна выполнять реальную работу, вовремя возвращать правильный контекст и заметно улучшать разговор.
2. **Real-World Use.** Бот должен быть развёрнут и использован реальными людьми; доказательства «до/после» должны быть убедительными.
3. **Build Quality.** Интеграция должна быть чистой, документированной и воспроизводимой.
4. **Best Article.** Статья должна понятно показывать продукт, интеграцию памяти и изменение поведения бота и быть полезной новому разработчику.

Дополнительный конкурсный трек **Beyond the Big Two** допускает одновременную победу с основным треком, если основная модель не предоставлена OpenAI или Anthropic. Выбор модели пока не зафиксирован.

## Текущие архитектурные решения

- Telegram выбран как самый короткий путь к доступному реальным пользователям MVP.
- Backend остаётся главным доверенным компонентом: он хранит секреты, определяет пользователя, вызывает память и LLM.
- Идентификатор Telegram-пользователя служит основой изоляции памяти, но не должен бездумно включаться в публичные данные.
- Recall выполняется до вызова LLM; релевантные memories добавляются к system/context prompt вместе с коротким контекстом текущего диалога.
- После хода пользователя выполняется извлечение долговременных фактов через `analyze`/`remember` либо через `withMemWal` с `autoSave`, если актуальное поведение middleware подходит требованиям.
- На первом этапе предпочтителен Default SDK: relayer выполняет embedding, шифрование, загрузку в Walrus, поиск и восстановление. Manual SDK не нужен без отдельной причины.
- Основной источник истины для долгосрочной памяти — Walrus Memory на Mainnet. Локальное состояние допустимо лишь для краткой текущей сессии, очередей и технической наблюдаемости.
- Сохранение всего transcript запрещено как стратегия по умолчанию: это ухудшает качество recall, приватность и управляемость.
- Любые возможности `/memory` и `/forget` необходимо проектировать по реально доступному API текущей версии, а не по предположениям.
